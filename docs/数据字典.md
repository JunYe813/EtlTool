# 数据字典 —— Olist 巴西电商数据集

> 来源：Kaggle 公开数据集《Brazilian E-Commerce Public Dataset by Olist》
> 原始路径：`EtlData\data`
> 规模：约 10 万订单、2016-2018 两年、巴西全国
> 语言：字段为葡萄牙语（英文词根），类目名葡语需 join 翻译表
> 用途：ODS 数据源（替代自造数据）

---

## 一、表关系（ER 关系图，文字版）

```
olist_customers（买家） 1 ── * olist_orders（订单主表） 1 ── * olist_order_items（明细）
                                 │   1 ── * olist_order_payments（支付）
                                 │   1 ── * olist_order_reviews（评价）
                     olist_products（商品） * ── 1 明细
                     olist_sellers（卖家）   * ── 1 明细
                     olist_geolocation（邮编地理，可选，60MB）
```

**主从结构**：`orders`（主）— `order_items`（从），一个订单多件商品多卖家。

## 四、天然脏数据点（面试可讲的清洗清单）

1. `product_name_lenght / description_lenght`：原数据集字段名拼写错误 → 清洗时列改名
2. `product_category_name` 有空值 → 标 unknown 或 join 翻译表
3. `order_status` 8 种取值 → 归一枚举（delivered 等）
4. `review_comment_title/message` 大量空值 → 空值策略（保留 NULL）
5. `customer_id` 不等于唯一买家 → 用户分析用 customer_unique_id
6. 明细金额核对：订单实付 vs Σ(items price+freight) vs Σ(payments) —— 你的对账经验直接用上
7. CSV 带引号包裹 → 导入时注意 quoting

## 五、口径建议（沿用大纲，微调）

- **销售日口径**：用 `order_purchase_timestamp`（下单日）或 `order_approved_at`（确认日）——写死一个，建议下单日
- **GMV 口径**：已支付（status 非 canceled/unavailable/created）订单的 Σ(明细 price)，不含运费
- **时间跨度**：2016-2018 两年，留存/复购随便算（30/60/90 日留存都能做）
  > 补充实测：**有效订单**的购买日实际只到 `2018-09-03`（`dwd_order` 全量到 2018-10-17，
  > 但之后全是 canceled/unavailable）。有效购买日共 614 天。

## 六、DWS / ADS 对象清单（已实现）

口径常量集中在 `config.py`（`VALID_STATUSES` / `RETENTION_WINDOWS` / `TOP_N` 等），
改一处即全局生效。

### DWS 层（按维度预聚合）

| 对象 | 粒度 | 关键字段 | 看板用途 |
|---|---|---|---|
| `dws_sale_daily` | 购买日 × 英文类目 × 卖家州 | order_cnt / item_cnt / gmv | 类目占比 / 州对比 / 日趋势 |
| `dws_sale_daily_seller` | 购买日 × 卖家 | order_cnt / item_cnt / gmv | 「店铺 TopN」区块（支持卖家州筛选） |
| `dws_sale_daily_product` | 购买日 × 商品 | order_cnt / item_cnt / gmv | 「单日单品 TopN」区块 |

> ⚠️ 三张 DWS 表的 `order_cnt` 都**不可跨维度相加**（一单可含多类目 / 多卖家 / 多商品），
> 但**跨天可以相加**（一个订单只属一个购买日）。详见第八节第 1 条。

### ADS 层（指标表 + 视图）

| 对象 | 粒度 | 关键字段 | 说明 |
|---|---|---|---|
| `ads_sale_overview_daily` | 购买日 | gmv / freight_total / paid_amount / order_cnt / item_cnt / buyer_cnt / avg_order_value | 客单价口径写死在表里，看板不再重算 |
| `ads_top_product` | 购买日 × 商品 | rank_no / gmv | 每日 Top10，ORDER BY 加了 product_id 兜底 |
| `ads_top_seller` | 卖家 | gmv / order_cnt / item_cnt / avg_item_price | 全周期榜，不随日期筛选（按日的卖家粒度见 `dws_sale_daily_seller`） |
| `ads_user_retention` | cohort 首购日 | cohort_size / observable_days / retention{7,30,60,90}d_{count,rate} | 宽表，rate 为 `NUMERIC(10,4)` |
| `ads_user_repeat_overall` | 全周期（1 行） | buyer_cnt / repeat_buyer_cnt / repeat_rate / orders_per_buyer | 单值 metric |
| `ads_user_repeat_monthly` | 首购月 | buyer_cnt / repeat_buyer_cnt / repeat_rate | 趋势线，末月有右删失 |
| `ads_fulfillment_monthly` | 购买月 | 各级 count/rate、avg_*_days、late_rate | **全量订单**口径 |
| `v_sale_daily_category` | 日 × 类目 | gmv / item_cnt | 只暴露可加指标 |
| `v_sale_daily_seller_state` | 日 × 卖家州 | gmv / item_cnt | 同上 |
| `v_sale_daily_buyer_state` | 日 × 买家州 | order_cnt / gmv | 订单粒度，可加 |
| `v_fulfillment_funnel` | 购买日 | 各级 count、avg_*_days | 全量订单口径 |
| `v_retention_curve` | cohort × 窗口（长表） | window_days / retained_cnt / retention_rate / **is_complete** | `is_complete=false` 即右删失 |

### ETL 控制表（元数据，不属于四层）

| 对象 | 粒度 | 关键字段 | 说明 |
|---|---|---|---|
| `etl_watermark` | 任务名（1 行） | job_name / last_date / update_time | 记录「已处理到的购买日」。当前用一行 `job_name='incremental'`；`last_date` 用 `GREATEST` 更新，**只前进不后退**（补跑历史日期不会把水位线拉回去） |

建表语句独立放在 `sql/load/00_watermark.sql`（不在 `01_dwd.sql` 里），
因为它是**增量路径的私有依赖**：全量路径不需要它，增量路径没有它就跑不了。

增量路径共 3 个脚本，顺序即依赖顺序：

| 脚本 | 作用 |
|---|---|
| `sql/load/01_dwd_inc.sql` | `dwd_order_detail`（按 `purchase_date`）/ `dwd_order`（按 `purchase_at::date`）区间 `DELETE` + `INSERT` |
| `sql/load/02_dws_inc.sql` | 3 张 DWS 日汇总表区间 `DELETE` + `INSERT` |
| `sql/load/03_ads_inc.sql` | `ads_sale_overview_daily` / `ads_top_product` 按日、`ads_fulfillment_monthly` 按**月** `DELETE` + `INSERT`（删除区间要覆盖月份边界，见下） |

> **陷阱（实测复现过）**：`ads_fulfillment_monthly` 是**月**粒度，但增量参数是日区间。
> 删除范围**必须用 `>= start所在月 AND <= end所在月` 的区间**，
> 不能写成 `IN (trunc(start), trunc(end))` —— 当回看窗口跨 ≥3 个月时
> （如 `--lookback 90`），中间月份不在 `IN` 列表里 → 漏删，紧接着被 `INSERT` 重插，
> 撞上 `PRIMARY KEY (purchase_month)`，增量任务报
> `duplicate key value violates unique constraint` 直接中断。
> 默认 `--lookback 3` 最多跨 2 个月，所以这个坑平时看不出来。
>
> 顺带一个值得讲的点：**主键把「静默算错」变成了「响亮失败」**。
> 如果这张表没主键，漏删的月份会变成重复行，履约订单合计从 99,441 虚增而无人察觉；
> 有了主键，同样的缺陷直接抛错、并在 `engine.begin()` 事务里整体回滚，不会留下半成品。

### 视图设计约束（重要）

看板带日期筛选，因此视图**必须保留日期粒度**，且**只暴露可加指标**：

- ✗ 不要在视图里直接 `GROUP BY 类目` 并用窗口函数算好占比 ——
  按日期筛选后分母仍是全周期总额，占比加起来不等于 100%
- ✗ 不要暴露跨天不可加的去重指标（如 `buyer_cnt`）
- ✓ 视图只给「日 × 维度」粒度的 gmv / item_cnt / order_cnt，
  占比、客单价等派生指标由看板在**筛选后的数据集**上现算

### 列的可加性速查

| 列 | 跨天可加 | 跨维度（类目/州/卖家）可加 |
|---|---|---|
| `gmv` / `freight_total` / `paid_amount` / `item_cnt` | ✅ | ✅ |
| `order_cnt`（`dwd_order` / `ads_sale_overview_daily`） | ✅ | — |
| `order_cnt`（`dws_sale_daily`） | ✅ | ❌ 跨类目/跨州会重复计数 |
| `buyer_cnt`（日表） | ❌ | ❌ |
| 各类 `*_rate` | ❌ 不可平均，需用分子分母重新相除 | ❌ |

## 七、存储策略与市面对照

> 本节回答两个高频问题：**每层该用什么主键、增量该怎么做**，以及**本项目与市面主流数仓的差距在哪**。

### 7.1 市面主流数仓的 5 条核心实践

| # | 实践 | 具体做法 |
|---|---|---|
| 1 | **按天分区是第一原则** | Hive/Spark：`PARTITIONED BY (dt string)`；**分区是增量的最小单位** |
| 2 | **增量 = 分区覆盖写** | `INSERT OVERWRITE TABLE t PARTITION(dt='...') SELECT ...`；重跑即幂等 —— 这是最主流的幂等方案，**而不是 UPSERT** |
| 3 | **维度变化用拉链表 SCD2** | `start_date` / `end_date` / `is_current` |
| 4 | **DWD 必做去重保留最新** | `ROW_NUMBER() OVER (PARTITION BY 业务主键 ORDER BY 更新时间 DESC) = 1` |
| 5 | **命名 `层_业务域_粒度_周期`** | `dwd_trade_order_detail_di`、`dws_trade_shop_1d` |

> 关于第 2 条：**Hive 传统表不支持 UPDATE/DELETE**，所以在大数据侧「能不能用 UPSERT」这个问题长期不存在 —— 标准答案就是分区覆盖写。UPSERT / MERGE 是数据湖（Delta Lake / Iceberg / Hudi）时代才普及的。

### 7.2 增量合并的三代做法，以及 PostgreSQL 的能力边界

| 做法 | 能力 | 本项目的 PG 16 |
|---|---|---|
| **UPSERT**（`ON CONFLICT DO UPDATE`） | 插入 + 更新 | ✅ |
| **MERGE**（完整 SQL:2003 语法） | 插入 + 更新 + **删除源里已消失的行** | ❌ **不支持 `WHEN NOT MATCHED BY SOURCE`** |
| **MERGE**（PG 实际支持的子集） | 插入 + 更新 + 条件删除**匹配到的**行 | ✅ |
| **分区覆盖写** | 全部（整分区替换） | 用 `DELETE 区间 + INSERT` 等价实现 |

**实测**（PostgreSQL 16.14）：

```
MERGE INTO _t t USING _s s ON t.id = s.id
WHEN MATCHED THEN UPDATE SET v = s.v
WHEN NOT MATCHED THEN INSERT (id, v) VALUES (s.id, s.v)
        → ✓ 成功，但源里已消失的 id=9 仍留在目标表（"幽灵行"）

... WHEN NOT MATCHED BY SOURCE THEN DELETE
        → ✗ syntax error at or near "BY"
```

**结论**：市面主流用 `MERGE INTO ... WHEN NOT MATCHED BY SOURCE THEN DELETE` 一条语句搞定增 / 改 / 删（SQL Server、Oracle、Snowflake、BigQuery、Delta Lake 都支持）。**而 PostgreSQL 的 MERGE 缺了这个子句**，删不掉「源里已消失的目标行」。

→ 在 PG 上，聚合层**只能**用 `DELETE 区间 + INSERT`。**这是引擎限制，不是设计选择。**

面试可讲的表述：

> "增量合并的标准做法是 MERGE。但 PostgreSQL 的 MERGE 不支持 `WHEN NOT MATCHED BY SOURCE`，删不掉源端已消失的行，所以我按引擎能力改用 DELETE 区间 + INSERT，语义等价于 Hive 的 `INSERT OVERWRITE PARTITION`。"

### 7.3 本项目逐层存储策略

| 层 | 对象 | 主键 | 写入方式 | 增量方式 |
|---|---|---|---|---|
| ODS | `olist_*_dataset` × 8 | **无主键** | append（一次性导入） | 不增量（源是静态 CSV；`imp_file_log` 防重） |
| DWD | `dwd_order_detail` | `(order_id, order_item_id)` | INSERT | **UPSERT 或 DELETE 区间** |
| DWD | `dwd_order` | `(order_id)` | INSERT | 同上 |
| DWS | `dws_sale_daily` × 3 | `(purchase_at, 维度…)` | INSERT | **必须 DELETE 区间** |
| ADS | `ads_sale_overview_daily` / `ads_top_product` / `ads_fulfillment_monthly` | 粒度键 | INSERT | **必须 DELETE 区间**（月表删整月） |
| ADS | `ads_top_seller` | `seller_id` | INSERT | **全量重建**（仅 3,053 行，比增量更简单） |
| ADS | `ads_user_retention` / `ads_user_repeat_*` | cohort / 首购月键 | INSERT | **必须全量**（cohort 定义会变） |
| 视图 | `v_*` | — | `CREATE OR REPLACE` | 定义未变则不重建 |

### 7.4 核心判断法则：「一行代表什么」决定键与增量方式

| 一行代表 | 键用什么 | 增量怎么做 | 本项目对应 |
|---|---|---|---|
| **一条业务记录** | 业务唯一键 | UPSERT 或 DELETE 区间 | `dwd_order` / `dwd_order_detail` |
| **一个维度组合的聚合值** | 维度组合键 | **必须 DELETE 区间** | `dws_*` / `ads_*` 日表 |
| **一次状态流转 / 推送动作** | 批次号 | 追加新记录 | 本项目无此形态 |
| **cohort 的统计结果** | cohort 键 | **必须全量重建** | `ads_user_retention` / `ads_user_repeat_*` |

**为什么聚合行不能用纯 UPSERT**（实测）：聚合表一行代表「某组合的汇总」。当某组合**重算后不再产生**时，UPSERT 无从冲突，旧行会留下成为**幽灵行**。实测一行幽灵数据让当日 GMV 从 `30,878.56` 变成 `1,030,878.55` —— **虚高 33 倍**。

> 集成平台类的系统（把数据推送到下游 ERP）常见另一种「汇总表」形态：以**批次号**为主键、并记录本批涉及的源单据号清单（如 `IoIds`）。因为它的用途是**推送任务载体** —— 要能按批次追溯、失败要按批次重推。
> 数仓的聚合表**不需要**记录源单据清单：**明细表本身就是血缘**，聚合值随时可重算，存一份副本反而多一个「两边不一致」的风险点。

### 7.5 本项目与市面主流的对齐情况

**已对齐 ✅**

| 项 | 说明 |
|---|---|
| 分层命名 | `ods_/dwd_/dws_/ads_` 前缀，符合数仓通行约定 |
| 增量用「覆盖」语义 | `DELETE 区间 + INSERT` ≈ Hive `INSERT OVERWRITE PARTITION` |
| 幂等 = 重跑结果一致 | 主流思想（而不是靠主键挡住重复插入） |
| DWD 建业务主键 | PG / MySQL 做数仓该建；Hive 里反而不建（仅 ACID 表支持） |
| ODS 原样留底 + 溯源列 | 对应主流 `ods_xxx` 层不做清洗 |

**未对齐 ⬜**

| 缺口 | 影响 | 补法 |
|---|---|---|
| **没有分区** | 增量只能整表 `DELETE`，产生死元组需 VACUUM；无分区裁剪 | 见 7.6 |
| **维度是 SCD1** | 商品 / 卖家 / 客户直接 join 当前值，维度改了会**追溯改历史** | 建 `dim_*_scd` 拉链表（SCD2） |

### 7.6 待补：把 `dwd_order_detail` 改成分区表

```sql
CREATE TABLE dwd_order_detail (
    order_id       varchar(100) NOT NULL,
    order_item_id  int          NOT NULL,
    purchase_date  date         NOT NULL,
    ...,
    -- ⚠️ PostgreSQL 约束：分区表的主键必须包含分区键
    PRIMARY KEY (order_id, order_item_id, purchase_date)
) PARTITION BY RANGE (purchase_date);

CREATE TABLE dwd_order_detail_2016 PARTITION OF dwd_order_detail
    FOR VALUES FROM ('2016-01-01') TO ('2017-01-01');
```

**收益**：

- 增量时 `DELETE WHERE purchase_date = X` → 可换成 `DETACH` / `DROP` 分区，**秒级且不产生死元组**
- 查询自动**分区裁剪**（`WHERE purchase_date BETWEEN ...` 只扫相关分区）
- 面试可讲：这是「数据量涨到 10 亿怎么办」的标准答案之一

**代价（真实取舍）**：主键必须从 `(order_id, order_item_id)` 变成 `(order_id, order_item_id, purchase_date)`，所有涉及该表的 SQL、以及 `check_idempotent.py` 的指纹逻辑都要跟着确认。

→ **建议放在增量改造完成之后单独做**，别两件事搅在一起。

## 八、已实测确认的口径陷阱（会算错数字，务必遵守）

### 1. `dws_sale_daily.order_cnt` 不可跨行相加
该表按 日×类目×卖家州 拆分，跨类目订单（**785 单**）/ 跨卖家州订单（**509 单**）会被多行重复计数。

| 算法 | 结果 |
|---|---|
| `SUM(order_cnt) FROM dws_sale_daily` | **99,279** ❌ |
| `COUNT(*) FROM dwd_order WHERE is_valid` | **98,202** ✅ |

→ 拿前者算客单价得 135.92，正确值是 **137.41**。
**订单粒度指标一律走 `dwd_order`。**

### 2. `ads_sale_overview_daily.buyer_cnt` 不可跨天相加
跨天复购的买家每天各计一次。

| 算法 | 结果 |
|---|---|
| `SUM(buyer_cnt) FROM ads_sale_overview_daily` | **97,272** ❌ |
| `COUNT(DISTINCT customer_unique_id) FROM dwd_order WHERE is_valid` | **94,986** ✅ |

差异来自 **2,064 个买家在多天购买**。区间去重买家必须现算。

### 3. 平均履约时长不能用「均值的均值」
直接 `AVG(avg_deliver_days) FROM ads_fulfillment_monthly` 得到 **14.31 天**（错），
因为它给订单量很小的月份和 1 月同等权重。
正确做法是按签收单量加权：`Σ(月度均值 × 签收数) ÷ Σ签收数` = **12.50 天** ✅。

### 4. 留存有右删失（right censoring）
`observable_days = 数据最大有效购买日 − cohort_date`。
当 `observable_days < N` 时该 cohort 的 N 日留存尚未观察完整，数值必然偏低。

- 有效订单最大购买日 = `2018-09-03`
- 因此 `2018-06-05` 之后（共 **86 天**）的 cohort，90 日留存均不完整
- 看板必须用 `is_complete` 过滤；月复购率表的最后 1~2 个月同理

### 5. 小样本会把留存率放大成噪声
`cohort_size = 1` 时，该买家恰好复购就得到 100% 留存。
实测历史数据里出现过 `cohort_date = 2016-12-23, cohort_size = 1, 30 日留存 = 1.00` 的记录。
→ 看板用 `cohort_size >= 20`（`config.MIN_GROUP_SIZE`）过滤。

### 6. 并列排名导致结果不可复现
`ROW_NUMBER() OVER (PARTITION BY purchase_date ORDER BY SUM(price) DESC)` 在并列时排名分配任意。
实测有 **20 天**存在「第 10 名与第 11 名 GMV 完全相同」的并列，
两次重跑入榜商品会不同。
→ 已给 `ORDER BY` 加 `product_id` 兜底。

### 7. `is_valid` 的口径例外（3 笔订单）
有 **3 笔**订单 `is_valid = true` 但无明细（状态 `invoiced`/`shipped`，`gmv = 0`）。
因为第五节把 `is_valid` 定义为「只由 `order_status` 决定」，所以不擅自改动，
由 `dwd_order.quality_flag = '异常-无明细但已发货/已开票'` 标记待业务确认。

**影响**：ADS 订单数与客单价分母包含这 3 单（3 / 98,202），GMV 不受影响（它们是 0）。
如需剔除，在 ADS 层加 `AND item_count > 0`，**不要**去改 DWD 的 `is_valid`。

### 8. 留存率精度：`NUMERIC(10,2)` 存不下 1~3% 的比率
Olist 30 日留存本身只有 0.66% 量级，2 位小数的 `NUMERIC(10,2)` 会把
`ROUND(..., 4)` 的结果砍成 0.00/0.01。
实测 613 个 cohort 里有 **498 个**的 7 日留存显示为 0。
→ 已改为 `NUMERIC(10,4)`。
