# 部署到服务器（腾讯云 Ubuntu 24.04 · 2 核 2G）

把 ETL 从「只在本地笔记本上跑、通过端口转发连远程 PG」迁成
「代码 + 数据库 + 调度都在服务器上，同机直连」。

```
腾讯云 Linux 服务器（2C2G / 40G 盘）
├── PostgreSQL 16 :5432         数仓 etl_data（已在跑）
├── Docker
│   └── ubuntu-postgres-1       当 Airflow 元数据库（已 idle 在跑，几乎不占内存）
├── Airflow（原生 venv）         scheduler + webserver，不开 triggerer
└── /opt/etl_data              项目代码（git clone）
```

---

## 服务器实测现状（2026-09）

| 项 | 值 |
|---|---|
| CPU / 内存 | 2 核 / **1.9 GiB** |
| 可用内存 | **929 MiB**，swap 已用 508 MiB ⚠️ |
| 磁盘 | 40G，已用 13G，**可用 25G** |
| 系统 / Python / Docker | Ubuntu 24.04.4 / Python 3.12.3 / Docker 29.7.2 |

**谁在吃这 2G：**

| 占用方 | 大致内存 | 处置 |
|---|---|---|
| PostgreSQL 原生（数仓） | ~300-400 MB | 保留 |
| **Hadoop / HDFS** | **~295 MB** | **停掉**（HDFS 数据在盘上，随时能起） |
| VS Code Server | ~372 MB | 你连着的时候才有，远程开发必需 |
| Docker 容器 | 11 MB | `postgres` 7.8MB 几乎空闲 → 拿来当 Airflow 元数据库 |
| 云镜 YDService | 68 MB | 保留 |

> ⚠️ **关键约束**：Airflow 官方建议 4GB 内存，这台只有一半。
> 所以下面全部走「最小化配置」：不开 triggerer、webserver 单 worker、并行度压到 1~2。

## 第 0 步 · 停 Hadoop（先释放 ~295MB）

```bash
jps                                    # 看当前有哪些 Hadoop 进程
echo $HADOOP_HOME                      # 确认路径，一般是 /usr/local/hadoop

stop-yarn.sh                           # 先 YARN
stop-dfs.sh                            # 再 HDFS（数据在盘上，不会丢）

jps                                    # 应该只剩 Jps
free -h                                # available 应从 ~929Mi 涨到 ~1.2Gi
```

如果 `stop-*.sh` 找不到，用绝对路径：`/usr/local/hadoop/sbin/stop-dfs.sh`。

> 如果配过开机自启（systemd / crontab），一并关掉，否则重启后又会占回来：
> `systemctl list-units | grep -i hadoop`、`crontab -l`

## 第 1 步 · 迁代码 + 建轻量 venv

> ⚠️ **前置条件：本地代码必须先 push 到 GitHub。**
> `git clone` 只能拿到**已推送**的代码。本地还有未提交/未推送的改动时，
> 服务器上会是旧版本 —— 而且**不会报错**，只会"少文件"，属于很难发现的那类问题。
>
> 推送前在本地确认两件事：
> ```powershell
> git status                 # 工作区应该干净（或只剩你故意不提交的）
> git log --oneline origin/main..main    # 有输出 = 有提交没推上去
> ```

只需要传 **1.5MB 代码**。不要传这些：

| 内容 | 体积 | 为什么不用传 |
|---|---|---|
| `venv/` | 416.8 MB | 服务器上重建 |
| `data/`（9 个 CSV） | 115.5 MB | 增量路径读 PG 里的 ODS 表，**不读 CSV** |

```bash
sudo mkdir -p /opt && sudo chown $USER:$USER /opt
cd /opt
git clone https://github.com/JunYe813/EtlTool.git etl_data
cd etl_data

python3 -m venv venv
venv/bin/pip install -r requirements-etl.txt      # 约 150MB / 30 秒
```

之后每次更新代码：本地 push → 服务器拉。

```bash
cd /opt/etl_data && git pull
```

### 备选：不想每次都提交推送，用 rsync 直接同步

调试阶段改代码频繁时可以让本地直接同步（**长期还是走 git**，
否则服务器上的目录会变成一份"来路不明"的副本）：

```powershell
# 在你本地电脑（PowerShell）执行
rsync -avz --delete `
  --exclude 'venv/' --exclude '.git/' --exclude 'data/' `
  --exclude '.tmp/' --exclude '__pycache__/' `
  "D:/Work/wujunye/PracticeSpace/EtlData/" ubuntu@<服务器IP>:/opt/etl_data/
```

> ⚠️ `--delete` 会让服务器目录**严格对齐**本地，包括删掉本地已删的文件。
> 别把它指向服务器上手工改过东西的目录。
> 另外 rsync 会覆盖 `.env` —— 服务器那份 `.env` 和本地不同（端口 5432 vs 5433），
> 传完记得检查，或者把 `.env` 也加进 `--exclude`。

> 本地 venv 是 417MB，服务器只装 ETL 那 4 个包 → 约 150MB。
> 看板的 `streamlit` / `altair` **不用装在服务器上**（见文末说明）。

## 第 2 步 · 配 `.env`（服务器版）

```bash
cp .env.example .env
vim .env
```

服务器上和本地不同，**同机直连，不走隧道**：

```ini
DB_HOST = 127.0.0.1
DB_PORT = 5432          # 服务器 PG 原生端口（本地那份是隧道的 5433）
DB_NAME = etl_data
DB_USER = postgres
DB_PASSWORD = 你的密码
FILE_PATH = /opt/etl_data/data     # CSV 没传，这个路径暂时用不到
```

> 两套环境对照，别混：
>
> | 环境 | `DB_HOST` | `DB_PORT` | 说明 |
> |---|---|---|---|
> | 本地笔记本 | `127.0.0.1` | `5433` | 端口转发到服务器 |
> | **服务器** | `127.0.0.1` | `5432` | 同机直连 |
>
> `.env` 已在 `.gitignore` 里，密码不会进 git。

## 第 4 步 · 装 Airflow（原生 venv）

### 为什么用原生 venv 而不是 Docker

| | 原生 venv | Docker |
|---|---|---|
| 磁盘 | ~1.5 GB | 镜像 ~4.5 GB |
| 进程控制 | 精确（只起 scheduler + webserver） | compose 默认一堆服务，要自己裁 |
| 2G 内存 | 无容器层开销 | 多一层 |

### 为什么锁 2.10.x 而不用 3.x

Airflow 3.x 把组件拆得更细（API server / dag-processor / scheduler / triggerer 各自进程），
**对 2G 内存更不友好**。2.10.x 用 scheduler + webserver 两个进程就能跑起来。

```bash
cd /opt
python3 -m venv airflow-venv
source airflow-venv/bin/activate

# 版本以官方当前 2.10.x 最新补丁版为准（https://airflow.apache.org/docs/apache-airflow/stable/installation/）
AIRFLOW_VERSION=2.10.5
PYTHON_VERSION=3.12
CONSTRAINT="https://raw.githubusercontent.com/apache/airflow/constraints-${AIRFLOW_VERSION}/constraints-${PYTHON_VERSION}.txt"

pip install "apache-airflow==${AIRFLOW_VERSION}" --constraint "${CONSTRAINT}"
```

### 元数据库：用那个 idle 的 Docker PG

先确认它有没有做**持久化** —— 没有 volume 的话，容器一重建 Airflow 的运行历史就全没了：

```bash
docker inspect ubuntu-postgres-1 --format '{{json .Mounts}}' | python3 -m json.tool
docker port ubuntu-postgres-1                     # 看映射到宿主机哪个端口
docker inspect ubuntu-postgres-1 --format '{{range .Config.Env}}{{println .}}{{end}}' | grep -i postgres
```

建库建用户：

```bash
docker exec -it ubuntu-postgres-1 psql -U postgres -c \
  "CREATE USER airflow WITH PASSWORD '换成强密码';"
docker exec -it ubuntu-postgres-1 psql -U postgres -c \
  "CREATE DATABASE airflow OWNER airflow;"
```

> **备选**：如果那个容器没有持久化、或者你以后会删它，
> 就在数仓 PG（5432）上建一个独立的 `airflow` 库 —— 少一个变量，
> 代价是元数据和业务库同实例（备份策略不同，属于将就）。

### 环境变量

```bash
mkdir -p ~/airflow && cat > ~/airflow/airflow.env <<'EOF'
AIRFLOW_HOME=/home/ubuntu/airflow
AIRFLOW__CORE__EXECUTOR=LocalExecutor
AIRFLOW__DATABASE__SQL_ALCHEMY_CONN=postgresql+psycopg2://airflow:密码@127.0.0.1:容器映射端口/airflow

# DAG 目录直接指向仓库，DAG 也跟着 git 版本管理
AIRFLOW__CORE__DAGS_FOLDER=/opt/etl_data/dags
AIRFLOW__CORE__LOAD_EXAMPLES=False

# ---- 2G 内存的关键调参 ----
AIRFLOW__CORE__PARALLELISM=2
AIRFLOW__CORE__MAX_ACTIVE_TASKS_PER_DAG=1
AIRFLOW__CORE__MAX_ACTIVE_RUNS_PER_DAG=1
AIRFLOW__WEBSERVER__WORKERS=1
AIRFLOW__LOGGING__LOGGING_LEVEL=WARNING
EOF
```

初始化（首次）：

```bash
set -a; source ~/airflow/airflow.env; set +a
airflow db migrate                 # 2.7 以前叫 airflow db init
airflow users create --username admin --firstname admin --lastname admin \
  --role Admin --email you@example.com --password '换成强密码'
```

> ⚠️ 装完用 `airflow config list | grep -i <键名>` 核对键名 —— 不同小版本的键名偶有调整。

## 第 5 步 · systemd 托管（不开 triggerer）

```bash
sudo tee /etc/systemd/system/airflow-scheduler.service >/dev/null <<'EOF'
[Unit]
Description=Airflow scheduler
After=network-online.target docker.service
Wants=network-online.target

[Service]
Type=simple
User=ubuntu
Group=ubuntu
EnvironmentFile=/home/ubuntu/airflow/airflow.env
ExecStart=/home/ubuntu/airflow-venv/bin/airflow scheduler
Restart=on-failure
RestartSec=10s

[Install]
WantedBy=multi-user.target
EOF
```

`airflow-webserver.service` 同理，`ExecStart` 换成：

```
ExecStart=/home/ubuntu/airflow-venv/bin/airflow webserver --port 8080
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now airflow-scheduler airflow-webserver
systemctl status airflow-scheduler --no-pager
free -h          # 看常驻内存，确认还有余量
```

> **不要开 triggerer**：只有 deferrable operator 才需要它，本项目没有。

### 看 UI：建议走 SSH 隧道，不要开 8080 到公网

Airflow 的 Web UI 是管理员界面，直接暴露在公网风险高。你本来就在用隧道连 PG，同一条路：

```bash
# 在你本地电脑上执行
ssh -L 8080:127.0.0.1:8080 ubuntu@<服务器IP>
# 然后浏览器打开 http://localhost:8080
```

确实要开公网端口的话，安全组放行 8080 之后**务必先改掉默认密码**。

## 第 6 步 · 回补（这才是真正有意义的运行）

源 CSV 是静态的，**不会有新数据每天到达**，所以「每天 02:00 跑一次」是演示性质的。
真正能证明这套设计的是**逐日回补**：

> ⚠️ **命令按 `airflow dags --help` / `airflow dags trigger --help` 的实际输出校对过**
> （Airflow 2.10.5）。别凭记忆写 —— 这几个参数名在各版本之间改过好几次：
>
> | 子命令 | 日期参数 | 说明 |
> |---|---|---|
> | `dags trigger` | `-e/--exec-date` | **没有** `--logical-date`（那是 Airflow 3.x 的名字） |
> | `dags backfill` | `-s/--start-date`、`-e/--end-date` | 注意 `-e` 在 trigger 里是 exec-date、在 backfill 里是 end-date，**建议一律用长参数** |
>
> 另外：**没有顶层的 `airflow backfill` 命令**，回补走 `airflow dags backfill`。

```bash
# 0. 确认 DAG 没被暂停 —— 暂停状态下触发的 run 会一直是 queued，task 根本不会跑
#    （`airflow dags trigger --help` 里明确写了这一点）
airflow dags list | grep olist_warehouse_daily
airflow dags unpause olist_warehouse_daily

# 1. 先触发一天，去 UI 看 6 个 task 是否依次变绿
airflow dags trigger olist_warehouse_daily -e 2017-11-15

# 2. 回补先跑 3 天，确认机制没问题
airflow dags backfill olist_warehouse_daily \
    --start-date 2017-11-01 --end-date 2017-11-03

# 3. 全量回补（634 天，约 1 小时）
airflow dags backfill olist_warehouse_daily \
    --start-date 2016-09-04 --end-date 2018-10-17
```

> `airflow dags test <dag> <日期>` 也能跑一整天，但它是**进程内**顺序执行 6 个 task，
> 和真实的 scheduler → LocalExecutor → 子进程 路径不一样，调试时结论不能直接推广。
> 验证「回补能不能跑通」要用 `dags trigger` / `dags backfill`。

**期望的验收结果**：634 天逐日增量跑完后，21 个对象的指纹与全量重建完全一致。

```bash
venv/bin/python scripts/check_idempotent.py --all    # 21/21 MATCH
```

> 耗时预估：每天约 5~8 秒（含 `ads_full_only`），634 天约 **1~1.5 小时**。
> 嫌慢的话可以把 `ads_full_only` 拆成一个独立的低频 DAG（cohort 表本来也不需要每天重建）。

## 监控与排查

```bash
free -h                                  # 常驻内存
systemctl status airflow-scheduler airflow-webserver --no-pager
journalctl -u airflow-scheduler -n 100 --no-pager
tail -f ~/airflow/logs/scheduler/latest/*.log
docker stats --no-stream                 # 容器占用
```

**OOM 了怎么办**：

1. 先看是谁在吃内存（`ps aux --sort=-%mem | head`），常见是 VS Code Server 或忘了关的 Hadoop
2. 把 `AIRFLOW__CORE__PARALLELISM` / `MAX_ACTIVE_RUNS_PER_DAG` 再降到 1
3. swap 已有 1.9G，但**swap 用满会非常慢**（磁盘 IO），尽量别靠它
4. 实在挤不下 → 走下面的备选方案

## 备选方案 B · 不上 Airflow，用 systemd timer

如果实测内存不够，或者你觉得 2G 的机器不值得为 Airflow 处处妥协：
`scripts/etl_tasks.py` **本身就是为这条路准备的** —— 它在命令行上把每层拆开了。

```bash
# /etc/systemd/system/olist-etl.service
[Service]
Type=oneshot
User=ubuntu
WorkingDirectory=/opt/etl_data
ExecStart=/opt/etl_data/venv/bin/python scripts/etl_tasks.py --layer dwd --target 2017-10-28
```

配 `olist-etl.timer` 定时触发，常驻开销约 30MB。

这条路要自己补：**重试、依赖顺序、失败告警、回补** —— 大概 100 行脚本。
但顺带说一句：你求职大纲里要求的那句「调度概念：DAG 依赖 / 失败重试 / 告警 /
**与 crontab 的分工**」，正好就是这个方案要回答的问题。
